## Title

Record provenance envelopes and append-only StatusEvent negative knowledge.

## Phase

P1

## Objective

Add the provenance envelope and the `StatusEvent` stream in about one and a half days, so a hypothesis row has no status column and a derived run can be repeated from its envelope.

## Problem

The scaffold can name a package and cannot yet record parameters or negative knowledge. Putting `rejected` on the hypothesis row, or storing only a parameter hash, would violate the data model before any join exists.

## User or scientific outcome

A benchmark operator can construct an envelope that contains the full parameter blob and can append `rejected` without rewriting hypothesis content. No join is ranked and no scholar decision is recorded.

- `ProvenanceEnvelope`, `AlgorithmRun`, and `StatusEvent` in [DATA_MODEL.md](../docs/DATA_MODEL.md).
- [ADR-0004](../docs/adr/0004-immutable-sources-and-provenance.md) and [ADR-0006](../docs/adr/0006-append-only-hypotheses.md).

## Outputs

- An in-memory provenance envelope and an in-memory `StatusEvent` stream.
- Tests that a repeated completed-run id matches, and that appending `rejected` does not mutate hypothesis content.

## Acceptance criteria

- [ ] The envelope stores `source_hashes`, the full `parameter_blob`, `parameter_hash`, `algorithm_name`, `algorithm_version`, `model_hash`, `code_version`, `decoder_name`, and `decoder_version`. Hash fields use the `sha256:` prefix. `model_hash` is `absent` when the run uses no model. It is never omitted and never empty.
- [ ] `random_seed` is a JSON integer when the algorithm used randomness and is omitted when the algorithm is deterministic. The completed-run id uses that integer or the token `absent`.
- [ ] A completed `AlgorithmRun` id follows the data-model array and includes no `attempt_id`. A cancelled or failed run inserts `attempt_id` after the status word and does not take the completed id. Timestamps are not in the id. Status is not rewritten.
- [ ] Hypothesis content has no status field. Current status is the latest `StatusEvent` for `target_id`. The event id is a random UUID. The first event is `proposed`, or `rejected` when the same write is a machine rejection. Appending an event does not change the content id.
- [ ] A test assembly-shaped record can store `unplaced_fragment_ids`. This ticket does not search placements.
- [ ] About one and a half days. No network call.

## Tests

Synthetic in-memory records. Cover a deterministic envelope with no seed, a seeded envelope, a completed id reproduced on a second call, a failed id that differs by `attempt_id`, and a `rejected` event that leaves content bytes unchanged. No `benchmarks/` read and no project database.

## Provenance effects

The envelope type is the effect. Tests construct it. They do not write a project run directory.

## Non-goals

- Join ranking, language scores, and the validation service. Human rejection status `rejected-via-ValidationDecision` is a legal event value. Recording a `ValidationDecision` is a later phase.
- `contested` composition across assemblies, beyond storing the event type.
- Accepting the ADR-0007 project layout.
- Coordinate frames ([P1-04](P1-04.md)) and ingest ([P1-05](P1-05.md)).
