## Title

Rasterize the synthetic fixture with lighting variation and a SHA-256 image manifest.

## Phase

P1

## Objective

In about one and a half days, write uncompressed TIFF bytes for the geometry from [P1-06](P1-06.md), apply a named lighting variation, and record a SHA-256 manifest. Ground truth stays in the BenchmarkLabel store.

## Problem

The fixture contract requires a page image and a digest for every generated image. Geometry alone cannot be ingested. A TIFF library is still unapproved, so the writer has to be the standard library.

## User or scientific outcome

A benchmark operator can obtain synthetic TIFF bytes, their digests, and the lighting parameter inside the same blob that already names erosion, rotation, and missing-fragment percentage.

## Inputs

- Geometry, placements, and the parameter blob from [P1-06](P1-06.md).
- The manifest rules in the synthetic-tear section of [EVALUATION.md](../docs/EVALUATION.md), after [P0-05](P0-05.md).
- Hash functions from [P1-02](P1-02.md).

## Outputs

- Uncompressed TIFF bytes for the generated page and for each emitted fragment.
- Manifest entries of `sha256:` digests.
- Lighting variation stored in the generator parameter blob.

## Epistemic-class impact

no. Pixels of a synthetic fixture are generator output. They are not a scholarly reading. Labels remain BenchmarkLabel records.

## Schema impact

none. Images and the manifest are fixture files. They are not a project evidence database and they are not written to `originals/`.

## Algorithm and benchmark impact

Extends the generator from [P1-06](P1-06.md). Tests check digests and determinism. They do not change BenchmarkLabel joins to pass.

## New dependencies

none. The writer emits uncompressed TIFF with the standard library. No Pillow and no NumPy.

## Acceptance criteria

- [ ] Lighting variation is a named parameter in the canonical parameter blob and participates in the `sha256:` parameter hash. The same seed and parameters reproduce the same bytes.
- [ ] Each generated image is an uncompressed TIFF whose magic is `II*\x00` or `MM\x00*`, so [P1-05](P1-05.md) can recognize it. The manifest lists a `sha256:` digest and byte length for every image.
- [ ] The envelope records decoder name and version for this writer. `model_hash` stays `absent`. `random_seed` stays present.
- [ ] Ground truth is not copied into the manifest or into any project database. Solver code does not read `benchmarks/`.
- [ ] About one and a half days. No network call. Generated images are test outputs, not committed fixtures.

## Tests

Generate into a temporary directory. Hash the TIFF bytes, parse only the magic and the documented width and height of this writer, and ingest one image through the [P1-05](P1-05.md) use case. A tampered byte must produce an `IntegrityFailure`. Do not commit the images.

## Provenance effects

Fills `decoder_name` and `decoder_version` on the generator envelope. The parameter blob still includes missing-fragment percentage, edge erosion, rotation, lighting variation, and `random_seed`.

## Non-goals

- Choosing an external TIFF library. [Q-ENG-05](../docs/OPEN_QUESTIONS.md#q-eng-05) stays open.
- Realistic parchment color, ink, or warp. Lighting is a per-fragment gain applied to the raster.
- Storing the TIFF under a project `originals/` tree.
- Ranking joins.

## Required documentation

- Docstrings name the uncompressed TIFF layout and the lighting parameter, and cite the manifest list in [docs/EVALUATION.md](../docs/EVALUATION.md).
- Do not add the writer as an approved general TIFF decoder for arbitrary scans.

## Open questions this depends on

[P1-06](P1-06.md) and [P0-05](P0-05.md) come first. Q-ENG-05 stays open. This writer does not close it.
